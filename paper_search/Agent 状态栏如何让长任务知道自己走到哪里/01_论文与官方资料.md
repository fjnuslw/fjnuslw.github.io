# Agent 状态栏如何让长任务知道自己走到哪里：论文与官方资料

> 调研日期：2026-08-13
> 用途：为个人网站文章与配套 Skill 提供可追溯证据。
> 结论适用范围：工具调用型、执行时间较长、需要暂停恢复或多人协作的 Agent。
> 阅读约定：文中的“状态栏”指每轮提供给模型的一小段结构化运行状态；它可以显示阶段、待办、已验证结果、资源预算和阻塞原因。

## 一页结论

长任务里，模型经常需要回答五个问题：目标是什么、已经完成什么、当前卡在哪里、下一步允许做什么、哪些结果已经验证。完整对话通常能保留这些信息，可它们散落在不同轮次和工具输出里。状态栏把运行时维护的结构化状态投影成一段短文本，放在模型容易读取的位置，让每轮决策都能看到同一组关键事实。

调研支持以下判断：

1. **状态栏应当是运行状态的读取视图。** 完整事实保存在事件日志或持久化状态里；状态栏经过投影得到，允许压缩、替换和重建。
2. **计划、事实和验证结果要分开。** `todo` 表示准备做的事，`completed` 只记录已经通过工具结果、测试或人工确认的事项。
3. **可计算字段交给代码维护。** 文件是否存在、测试是否通过、剩余预算、工具调用次数、当前阶段，都可以由运行时确定。模型适合提议语义标签或解释异常，提议仍需经过校验。
4. **状态机负责约束，状态栏负责提示。** 状态机规定当前阶段允许的动作与转移；状态栏把这些约束显示给模型。单靠提示文本无法保证执行路径合法。
5. **暂停恢复需要精确快照。** 可序列化的 run state 或 checkpoint 保存恢复执行所需的数据。状态栏只保留决策相关摘要，不能替代快照。
6. **前缀缓存影响更新策略。** 替换靠近上下文尾部的旧状态，会让旧状态之后的 token 失去前缀命中；连续追加状态会积累旧版本。工程上更适合保留外部事件日志，并在阶段变化、验证门完成或异常出现时刷新一份紧凑状态。
7. **公开资料暂未给出“状态栏提升多少成功率”的通用结论。** StateFlow、ContextDistill 等工作能提供相邻证据，实验对象和状态栏设计仍有差异。文章应把理论依据、工程经验与作者方案分别标注。

## 研究问题

| 编号 | 问题 | 本文结论 |
| --- | --- | --- |
| Q-001 | 状态栏解决什么问题？ | 减少模型每轮从长轨迹中重新定位任务状态的负担，并让关键约束保持可见。 |
| Q-002 | 状态应存在哪里？ | 精确状态与事件存运行时；状态栏是按需生成的模型可见投影。 |
| Q-003 | 如何更新才可靠？ | 事件驱动 reducer 更新，字段带来源、版本和验证标记；转移由代码校验。 |
| Q-004 | 如何兼顾 KV Cache？ | 稳定内容靠前，动态状态靠后；外部保留事件日志，提示内只放当前紧凑视图。 |
| Q-005 | 如何落到 research-to-spec 类 Skill？ | 从任务契约生成初始状态，搜索、证据、规格和验证事件持续推进状态机，完成条件与产物核对绑定。 |

## 逐项证据卡

### S-001 《AI Agent 原理与实践》：Agent 状态栏

- 页面：<https://bojieli.github.io/ai-agent-book/book/chapter2/#agent-agent>
- 源文件：<https://github.com/bojieli/ai-agent-book/blob/main/book/chapter2.md>
- 类型：作者公开教材，C 级。

页面把状态栏描述为一段动态元信息，可包含任务进度、环境信息和工具调用次数。示例把它作为靠近上下文末尾的元消息提供给模型。书中给出两种更新办法：删除旧状态后放入新状态，或保留历次状态并持续追加。

页面还提出两个重要工程判断。第一，能由代码确定的字段应由代码更新，避免让模型每轮重新阅读长对话后生成整段摘要。第二，压缩状态会丢信息，出现计划外问题时仍需回查原始上下文。

正文可用表述：

> 状态栏是一份随执行事件更新的短视图。它把当前阶段、已验证结果和下一步约束集中到模型近期可见的位置。完整轨迹仍保留在外部，以便审计和重建。

使用边界：书中的 user-role 元消息属于一种实现示例，各 API 对角色、优先级和缓存前缀的处理不同。文章不应把该角色写成统一标准。

### S-002 StateFlow：把任务过程表达成状态机

- arXiv：<https://arxiv.org/abs/2403.11322>
- 题目：*StateFlow: Enhancing LLM Task-Solving through State-Driven Workflows*
- 类型：arXiv 预印本，A 级来源、预印本标记。

StateFlow 用状态和转移组织多轮任务。论文区分“流程落地”和“状态内子任务求解”：流程结构规定当前阶段，模型在该阶段内选择动作或生成内容。这个划分为状态栏提供了一条可执行解释：状态栏显示当前状态，运行时负责检查转移是否合法。

论文摘要报告，相对 ReAct，StateFlow 在 InterCode SQL 与 ALFWorld 上的成功率分别提升 13% 和 28%，成本分别降低约 5 倍和 3 倍。正文还包含更细的设置与不同口径，例如 ALFWorld 某些比较约为 2.5 倍，精化状态从 83.3 提升到 88.8，并伴随约 15% 成本下降。

数据边界：

- 这些数字来自论文选定的数据集、模型、提示与成本估算。
- 状态机由任务专家设计，转移规则带有任务知识。
- 实验比较的是完整 StateFlow 系统与基线，无法把增益单独归因给提示中的状态文本。
- 文章若引用数字，应写出数据集、基线和预印本身份，不能写成通用提升。

### S-003 ReAct：状态栏所处的轨迹环境

- arXiv：<https://arxiv.org/abs/2210.03629>
- ICLR 2023：<https://openreview.net/forum?id=WE_vluYUL-X>
- 类型：同行评审会议论文，A 级。

ReAct 让模型交错生成推理轨迹与任务动作，并接收环境观察。它提供了理解长任务上下文的基本单位：thought、action、observation 会持续累积，当前决定依赖前面多轮结果。

正文可用结论：工具型 Agent 的上下文会被动作和观察不断拉长。状态栏可视为对轨迹当前截面的结构化投影。

边界：ReAct 没有比较“有状态栏”和“无状态栏”，所以它只能解释问题场景。

### S-004 Lost in the Middle：长上下文里的位置敏感性

- ACL Anthology：<https://aclanthology.org/2024.tacl-1.9/>
- DOI：<https://doi.org/10.1162/tacl_a_00638>
- arXiv：<https://arxiv.org/abs/2307.03172>
- 类型：TACL 2024 论文，A 级。

论文在多文档问答与合成键值检索任务中改变相关信息的位置。多个模型在相关信息位于上下文开头或结尾时表现较好，位于中间时常出现下降。由此可以谨慎支持“关键状态需要保持显眼且稳定”的设计动机。

数据边界：

- 实验任务与长程工具 Agent 不同。
- 位置效应会随模型、上下文长度、任务和提示变化。
- 论文没有证明“尾部永远最好”，也没有测量状态栏。
- 正文适合写“长上下文利用存在位置敏感性”，避免写成固定注意力定律。

### S-005 Statecharts：状态层级与并发的理论背景

- DOI：<https://doi.org/10.1016/0167-6423(87)90035-9>
- 题目：*Statecharts: A Visual Formalism for Complex Systems*
- 类型：同行评审论文，A 级。

Harel 的 Statecharts 在有限状态机基础上加入层级、正交并发和通信表达，适合说明复杂任务为何需要父状态、子状态与并行分支。配套 Skill 可以用父状态表达“研究中”，用子状态表达“检索论文”“核对官方文档”，并在汇合点检查所有必要分支。

边界：这篇论文讨论通用复杂系统。把它映射到 LLM Agent 是本文的工程推导。

### S-006 Reflexion：经验记忆与运行状态的区别

- NeurIPS 页面：<https://papers.nips.cc/paper_files/paper/2023/hash/1b44b878bb782e6954cd888628510e90-Abstract-Conference.html>
- arXiv：<https://arxiv.org/abs/2303.11366>
- 类型：NeurIPS 2023 论文，A 级。

Reflexion 把反馈转成语言反思，并保存在情景记忆中，供之后的尝试使用。它提醒我们把“这次运行走到哪里”和“过去失败教会了什么”分成两层：前者要精确、及时、可恢复；后者允许提炼，服务跨尝试策略调整。

边界：论文没有给出状态栏字段或状态机协议。

### S-007 Generative Agents：观察、反思与计划的分层

- arXiv：<https://arxiv.org/abs/2304.03442>
- ACM 页面：<https://dl.acm.org/doi/10.1145/3586183.3606763>
- 类型：UIST 2023 论文，A 级。

论文通过记录观察、生成反思并检索相关记忆来支持长期行为，同时维护计划。它可用于解释为什么事件、派生摘要和计划需要独立字段：三者的更新频率、可信度和用途不同。

边界：实验以社会模拟为主，不能直接代表编码、研究或浏览 Agent。

### S-008 LangGraph Persistence：checkpoint、thread 与 store

- 官方文档：<https://docs.langchain.com/oss/python/langgraph/persistence>
- 类型：框架官方文档，B 级。

LangGraph 在 thread 内用 checkpointer 保存每一步的 state snapshot。文档将持久化能力与 human-in-the-loop、time travel、fault tolerance 联系起来；跨 thread 的信息可放进 Store。它提供一组清楚的工程边界：

- thread：一次连续会话或运行的标识；
- checkpoint：某一步可恢复的精确快照；
- state：图节点读取与更新的数据；
- store：跨运行共享的长期数据。

文章可借此说明：提示中的状态栏只是一份显示层，恢复执行要依赖 checkpoint；跨项目经验应进入长期存储，不能混入当前任务的完成事实。

边界：具体字段、序列化器和 channel 行为绑定 LangGraph 版本。文档中的 DeltaChannel 等能力若仍标 beta，应在实现时查对应版本。

### S-009 Azure Event Sourcing：从事件重建状态

- 官方架构指南：<https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing>
- 类型：官方架构文档，B 级。

Event Sourcing 把状态变化记录为追加事件，当前状态通过顺序重放事件得到。指南同时讨论物化视图、定期快照、乐观并发、事件版本和 upcasting。映射到 Agent 后，可以形成如下链路：

```text
工具结果 / 人工输入 / 超时
          ↓
       事件日志
          ↓ reduce
      精确运行状态
          ↓ project
      模型可见状态栏
```

追加日志便于回答“谁在什么时候把哪一项标记完成”，也便于状态投影损坏后重新生成。快照缩短恢复时的重放距离，事件日志继续承担审计职责。

边界：官方指南明确提醒该模式复杂，会增加一致性、版本迁移和查询成本。短小、单轮、无需恢复的任务可以直接维护普通状态对象。

### S-010 Azure CQRS：状态栏作为物化读取视图

- 官方架构指南：<https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs>
- 类型：官方架构文档，B 级。

CQRS 将写入模型与读取模型分开。状态栏可以按这个思路实现：事件与运行时状态负责写入真相；给模型阅读的状态对象按决策需要投影，只保留阶段、门槛、下一步和风险。

正文可用结论：状态栏允许为阅读效率优化，前提是任何字段都能追溯到精确状态或事件。它发生错误时可以丢弃并重建。

边界：这是从通用架构到 Agent 的类比。文章应将其写成设计方法，避免声称 CQRS 官方文档直接讨论 LLM。

### S-011 OpenAI Agents SDK Context：本地上下文与模型上下文

- 官方文档：<https://openai.github.io/openai-agents-python/context/>
- 类型：SDK 官方文档，B 级。

文档区分本地 context 与 LLM 可见 context。本地 context 可保存依赖、日志器和业务对象，它不会自动发送给模型；模型只能看到输入、指令和工具等显式提供的内容。

这条边界直接支持三层设计：

1. 本地状态对象保存精确数据和内部句柄；
2. projector 选择少量字段；
3. 状态栏把字段转换成模型可读文本。

安全边界：包含密钥、访问令牌、个人信息或内部路径的本地对象不能直接序列化进提示。状态投影需要字段白名单和脱敏。

### S-012 OpenAI Agents SDK RunState 与 HITL：暂停恢复边界

- Python RunState：<https://openai.github.io/openai-agents-python/ref/run_state/>
- JavaScript RunState：<https://openai.github.io/openai-agents-js/openai/agents/classes/runstate/>
- JavaScript human-in-the-loop：<https://openai.github.io/openai-agents-js/guides/human-in-the-loop/>
- 类型：SDK 官方文档，B 级。

RunState 表达运行循环的可序列化状态。human-in-the-loop 指南展示在工具审批处暂停、序列化状态、之后恢复执行的模式。这说明“暂停后继续”需要保存比状态栏更完整的数据，例如当前 item、上下文、审批记录、生成状态和调用关联。

正文可用结论：

> 状态栏帮助模型在一轮开始时定位；run state 帮助执行器在中断后从正确位置恢复。两者可以来自同一状态对象，序列化深度不同。

边界：SDK 类型和序列化格式会演进。文章引用概念与官方页面，项目实现时仍需锁定版本并测试兼容性。

### S-013 OpenAI Codex agent loop：稳定前缀与缓存命中

- 官方工程文章：<https://openai.com/index/unrolling-the-codex-agent-loop/>
- 类型：官方工程说明，B 级。

文章说明 Agent 循环会重复携带较长前缀，prompt caching 对延迟和成本很重要。提升命中的原则包括保持已有前缀逐 token 一致，把静态内容放前面，把变化内容放后面。工具列表、模型、沙箱、工作目录或顺序变化都可能破坏缓存前缀。

状态栏由此得到两个工程约束：

- 动态字段靠近提示尾部，避免改动更早的稳定前缀；
- 更新文本要紧凑，避免旧状态版本持续占用上下文。

边界：该文章没有公开“某种状态栏布局节省多少 token 或延迟”的专项实验。实际收益依赖供应商缓存规则、最小缓存块、保留时间、路由和计价方式。

### S-014 vLLM Automatic Prefix Caching：缓存节省哪一段计算

- 用户文档：<https://docs.vllm.ai/en/v0.22.1/features/automatic_prefix_caching/>
- 设计文档：<https://docs.vllm.ai/en/v0.14.1/design/prefix_caching/>
- 类型：推理引擎官方文档，B 级。

Automatic Prefix Caching 复用相同前缀已经计算的 KV block，主要减少 prefill。文档明确指出，它不会减少新输出 token 的生成计算；当输出很长，或请求之间没有可复用前缀时，收益有限。

正文可用结论：缓存优化需要明确写“省了 prefill”，不能笼统写“推理变成常数成本”。即使前缀已缓存，模型生成每个新 token 时仍要处理当前上下文对应的注意力计算与 KV 读取。

版本边界：上面两个链接分别是 v0.22.1 用户页与 v0.14.1 设计页。实现细节以部署版本的文档和源码为准。

- 官方团队博客：<https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus>
- 类型：一线工程博客，C 级。

### S-016 ContextDistill：上下文蒸馏的收益与离分布风险

- 作者团队研究页：<https://01.me/research/context-distillation>
- 页面所列代码地址：<https://github.com/19PINE-AI/context-distillation>
- 类型：作者团队研究页，C 级。

## 跨来源综合结论

### F-001 状态栏是一份物化视图

证据链：S-001 + S-009 + S-010 + S-011。

事件日志保存发生过什么，运行状态保存当前精确值，projector 生成供模型阅读的状态栏。这个结构允许状态栏大胆压缩，也保留追溯和纠错入口。

理论与工程归属：Event Sourcing、CQRS 提供架构思想；把状态栏实现为物化视图属于本文工程推导。

### F-002 状态机与状态栏分工明确

证据链：S-002 + S-005。

状态机定义允许的转移和门槛，例如 `researching → synthesizing` 需要至少一项主来源且关键结论有来源映射。状态栏把当前状态、允许动作和未满足门槛显示给模型。执行器仍需拒绝非法转移。

### F-003 计划不能直接证明完成

证据链：S-001 + S-008 + S-009。

`planned`、`attempted`、`observed`、`verified`、`completed` 应有不同语义。工具调用成功只证明调用完成，产物存在、内容有效和用户目标达成都需要各自的验证事件。

### F-004 状态栏降低的是定位负担

证据链：S-003 + S-004 + S-015。

长轨迹把目标和结果分散在多轮 action/observation 中，模型对长上下文的利用又存在位置敏感性。把关键状态集中展示，可以减少每轮重新寻找信息的需要。现有证据不足以承诺统一准确率增益。

### F-005 精确恢复依赖 checkpoint

证据链：S-008 + S-012。

状态栏适合阅读，checkpoint 适合恢复。中断前保存精确 run state，恢复后重新投影状态栏，可以避免让模型依据旧摘要猜测执行位置。

### F-006 长期记忆、会话历史与当前状态需要分层

证据链：S-006 + S-007 + S-008 + S-017。

当前状态服务本次决策；会话历史保留交流；情景记忆保存可复用经验；跨 thread store 保存长期偏好或知识。混合后容易把旧任务结论误当成当前事实。

### F-007 动态内容放在稳定前缀之后

证据链：S-013 + S-014。

相同前缀才能复用既有 KV block。系统指令、工具定义和长期稳定规范靠前，当前状态和最新观察靠后，可以缩小每次更新导致的未命中范围。

### F-008 缓存只覆盖计算路径的一部分

证据链：S-014。

前缀缓存主要省去相同输入前缀的 prefill。输出 decode、动态后缀、缓存写入、KV 内存和上下文占用仍有成本。文章不能用 O(1) 描述整个 Agent 回合。

### F-009 追加与替换都存在代价

证据链：S-001 + S-013 + S-014。

替换旧状态能保持提示紧凑，但旧状态之后的前缀不再一致。持续追加保留缓存友好的前缀，却会留下过期版本，并让输入长度随更新次数增长。推荐策略是外部事件持续追加，提示内保留一份当前视图；只有需要审计的少量关键事件进入提示。

### F-010 摘要边界必须能回退

证据链：S-001 + S-016。

状态投影只覆盖设计时知道的查询。出现新问题时，应能读取原始事件、工具输出或产物。任何把摘要当作唯一事实存储的设计都会失去这种回退能力。

### F-011 状态字段需要来源和时效

证据链：S-009 + S-010。

关键字段至少携带 `revision`、`as_of_event`、`source`、`updated_at`、`verified`。多个事件同时更新时，使用 expected revision 或其他乐观并发手段防止静默覆盖。

### F-012 多 Agent 写状态要考虑幂等与冲突

证据链：S-005 + S-009。

并行研究分支可以各自产生事件，汇总器按事件 ID 去重并检查版本。一个结果重复回传时，幂等键避免计数两次；两个 Agent 同时改同一字段时，冲突需要显式解决。

### F-013 模型只提议高歧义字段

证据链：S-001 + S-011。

计数、路径、测试状态和预算由代码计算。主题标签、失败原因分类和下一步解释可由模型提议，运行时用 schema、枚举和来源检查约束结果。

### F-014 状态栏也是安全边界

证据链：S-009 + S-011。

外部网页、Issue 和用户文档中的文字不能直接成为 `allowed_actions`、`completed` 或高优先级指令。状态投影采用字段白名单，保留来源，过滤密钥与个人信息；高风险完成条件交给独立验证器。

### F-015 研究状态机需要粗粒度阶段

证据链：S-002 + S-005。

状态表示需要不同规则和门槛的阶段。一次搜索查询、打开一个网页、读取一段文件属于事件或动作。若把每个动作建成状态，转移图会快速膨胀，维护成本高于收益。

## 建议采用的六层状态模型

| 层 | 保存内容 | 典型寿命 | 是否直接给模型 | 失败后的恢复方式 |
| --- | --- | --- | --- | --- |
| 1. 任务契约 | 目标、范围、交付物、禁止项、完成条件 | 整个任务 | 摘要可见 | 用户确认或版本化修改 |
| 2. 事件日志 | 工具调用结果、文件变化、审批、错误、人工输入 | 可长期保留 | 按需检索 | 追加记录与重放 |
| 3. 精确运行状态 | 当前阶段、计数器、路径、分支、revision | 当前 run | 经过投影后可见 | 从 checkpoint 或事件重建 |
| 4. 状态栏 | 当前阶段、已验证事项、下一步、阻塞、预算 | 每轮刷新 | 可见 | 从精确状态重新生成 |
| 5. Checkpoint | 恢复执行所需的完整序列化对象 | 直到 run 结束或归档 | 通常不可见 | 反序列化恢复 |
| 6. 长期记忆 | 跨任务偏好、稳定规则、经验摘要 | 跨 run | 检索后可见 | 版本管理与过期清理 |

这六层可以共享 ID 和来源，但不应共用一段自由文本。任务契约与事件日志偏向证据；运行状态与 checkpoint 偏向执行；状态栏偏向阅读；长期记忆偏向复用。

## 一份可落地的状态对象

下面的例子面向 research-to-spec 工作流，字段名仅作建议：

```json
{
  "task_id": "agent-status-bar-article",
  "revision": 18,
  "phase": "verifying",
  "goal": "产出一篇有来源、有示例的 Agent 状态管理文章与配套 Skill",
  "deliverables": [
    {"id": "article", "status": "drafted", "verified": false},
    {"id": "skill", "status": "implemented", "verified": false}
  ],
  "evidence": {
    "primary_sources": 9,
    "official_sources": 8,
    "unsupported_claims": 2
  },
  "gates": {
    "source_traceability": "pass",
    "site_validation": "pending",
    "mobile_320px": "pending"
  },
  "blockers": [],
  "next_actions": [
    "补齐两条无来源结论",
    "运行站点验证",
    "检查 320px 排版"
  ],
  "as_of_event": "evt-0042",
  "updated_at": "2026-08-13T14:20:00+08:00"
}
```

### 字段设计原则

1. `revision` 单调增加，写入者提交时带上期望版本。
2. `phase` 使用小型枚举，避免模型自由发明阶段名。
3. 每个交付物单独记录 `status` 与 `verified`。
4. 计数器由程序从证据索引计算。
5. `next_actions` 只放当前可执行的少量动作，建议 1 到 3 项。
6. `as_of_event` 指向投影覆盖的最后事件，便于识别陈旧状态。
7. `updated_at` 用于诊断时效，不能独立证明字段正确。
8. 任何外部内容都保存在证据字段中，不能直接覆盖阶段和允许动作。

## 给模型看的紧凑状态栏

精确对象可以很详细，模型可见版本只需服务下一轮决策：

```text
<run_status revision="18" as_of_event="evt-0042">
phase: verifying
goal: 发布 Agent 状态管理文章与配套 Skill
verified: 来源映射通过
pending_gates: site-validation, mobile-320px
blockers: none
next: 补齐 2 条无来源结论；运行站点验证
rule: 只有验证器通过后才能进入 completed
</run_status>
```

状态栏里应少放：完整搜索历史、长篇反思、已经过期的 TODO、重复的工具输出、密钥、个人信息和无法验证的成功判断。

## 状态更新算法

### 1. 事件先落盘

每个工具结果转换为一个类型明确的事件：

```json
{
  "event_id": "evt-0042",
  "type": "validation_finished",
  "task_id": "agent-status-bar-article",
  "payload": {
    "validator": "node tools/validate-site.mjs",
    "exit_code": 0
  },
  "source": "local_process",
  "recorded_at": "2026-08-13T14:20:00+08:00",
  "idempotency_key": "validate-site:commit-sha"
}
```

### 2. Reducer 更新精确状态

伪代码：

```text
apply(state, event):
  assert event.task_id == state.task_id
  if event.idempotency_key already_seen:
      return state
  assert event is valid for state.phase
  next = deterministic_reduce(state, event)
  next.revision = state.revision + 1
  next.as_of_event = event.event_id
  return next
```

### 3. Projector 生成状态栏

```text
project(state):
  select goal, phase, verified facts, open gates, blockers, next actions
  redact secrets and internal-only fields
  limit list lengths and total tokens
  attach revision and as_of_event
  return schema-valid text
```

### 4. Runtime 检查模型动作

模型读取状态栏后仍可能选择越权动作。运行时根据 `phase`、工具权限和审批规则检查动作。失败时写入 `action_rejected` 事件，让下一轮看到明确原因。

## 推荐的研究型状态机

```text
intake
  ↓ 任务契约已确认
research_planning
  ↓ 问题树与来源策略已建立
researching
  ↓ 关键问题有足够证据
synthesizing
  ↓ 结论与来源已映射
specifying
  ↓ 规格含验收条件
verifying
  ├─ 验证失败 → researching / specifying
  └─ 全部门槛通过 → completed
```

旁路状态：

- `awaiting_input`：缺少会改变结果的用户选择；
- `blocked`：外部依赖持续不可用，当前无法继续；
- `cancelled`：用户终止；
- `failed`：不可恢复错误，保存诊断和恢复建议。

### 转移门槛示例

| 转移 | 最低门槛 | 验证者 |
| --- | --- | --- |
| intake → research_planning | 目标、交付物、范围已记录 | schema validator |
| research_planning → researching | 每个关键问题有来源策略 | plan validator |
| researching → synthesizing | 关键结论至少有一项 A/B 级来源，例外有标记 | evidence audit |
| synthesizing → specifying | 结论含适用条件和反例 | claim audit |
| specifying → verifying | 每项需求有验收方法 | spec audit |
| verifying → completed | 文件、测试、排版、索引全部通过 | 独立验证器 |

“搜索了十个网页”只表示投入量。“关键结论有主来源且链接可访问”才接近研究门槛。

## 状态栏在上下文中的位置

建议顺序：

```text
[稳定系统指令]
[稳定工具定义与输出协议]
[任务契约的稳定部分]
[历史轨迹 / 最新工具观察]
[当前状态栏]
[本轮请求]
```

这个顺序有三点理由：

1. 稳定内容尽量形成可复用前缀，符合 S-013 与 S-014 的缓存条件。
2. 当前状态靠后，减少被长轨迹埋在中间的风险，符合 S-004 提供的位置敏感性证据。
3. 本轮请求与状态相邻，模型更容易把允许动作和当前任务一起读取。

位置仍需按 API 行为测试。某些平台对 system、developer、user 或自定义消息有不同优先级和缓存规则。文章应把“靠后”写成可测试建议。

## 三种状态更新策略与 KV Cache 代价

### 策略 A：替换旧状态

每轮删除旧状态，再把新状态放到尾部。

优点：提示里只有当前版本，长度容易控制。
代价：旧状态之后若已有一段轨迹，这段后缀的 token 前缀位置会改变，可能重新 prefill。

适合：状态更新频繁、旧状态容易误导、动态后缀较短的任务。

### 策略 B：持续追加状态

旧状态保留，新状态继续加在末尾。

优点：已有前缀保持逐 token 一致，容易复用前缀缓存。
代价：状态历史二次增长，旧版本占上下文，还可能让模型引用过期字段。

适合：更新次数少、状态很短、平台缓存折扣高且能明确标记最新版的任务。

### 策略 C：外部追加事件 + 提示内当前投影

事件日志在提示外持续追加，运行时维护精确状态；提示内保留一份当前投影。阶段变化、门槛完成、阻塞或预算告警时刷新，普通细粒度事件只更新外部状态。

优点：保留审计能力，同时限制提示膨胀。
代价：需要事件存储、reducer、projector 与一致性测试。

这是本文推荐的默认方案。缓存收益要通过实际 token、cache hit、延迟和任务质量指标验证。

### 一个用于思考的简化公式

设：

- `S`：每份状态栏的 token 数；
- `R`：替换旧状态后需要重新 prefill 的平均后缀 token 数；
- `N`：任务中状态更新次数；
- `α`：缓存输入 token 相对未缓存输入 token 的价格比例，`0 ≤ α ≤ 1`。

忽略共同的稳定前缀后，可粗略比较两类额外成本：

```text
C_replace ≈ (N - 1) × (1 - α) × R
C_append  ≈ α × S × N × (N - 1) / 2
```

在这个简化模型里，追加策略较有利的条件近似为：

```text
α × S × N / 2 < (1 - α) × R
```

例 1（纯假设）：`α=0.1`、`S=200`、`N=10`、`R=800`。追加旧状态的加权成本约为 900 token-equivalent，替换导致的额外未缓存后缀约为 6480。该设定下追加看起来更省输入费用。

例 2（纯假设）：`α=0.5`、`S=300`、`N=50`、`R=100`。追加旧状态的加权成本约为 183750，替换约为 2450。频繁更新使状态历史迅速膨胀。

公式边界：

- 这是比较方向的草图，没有包含公共输入成本。
- 没有包含缓存最小块、TTL、路由漂移、缓存写入费和内存淘汰。
- 没有包含 decode、工具时间、上下文上限与状态过期造成的质量损失。
- `α` 必须取自实际模型与供应商当期价格，不能把示例数字当报价。
- vLLM 的 APC 关注计算复用，云 API 计价还受服务端策略影响。

因此，生产系统应记录每轮输入 token、缓存命中 token、输出 token、端到端延迟、状态长度、更新原因和任务结果，再决定策略。
