## 结论先行

现有博客的基础质量已经过关：本地资源链接完整，跳转到新窗口的链接都带 `noopener noreferrer`，导航、跳过链接、键盘焦点、减少动态效果等基础无障碍措施也已经存在。`node tools/validate-site.mjs` 在当前基线下通过，共检查 17 个 HTML 文件和 264 个本地资源链接。

本次维护最值得优先处理的内容有六项：

1. 删除 Hello World 时要同步清理文章文件、博客卡片、`posts.json` 和站点地图四处记录。
2. 《小 VLM…》在 320 px 窄屏下出现真实的横向溢出：页面可视宽度 315 px，文档宽度被第三张表撑到 370 px；全站又设置了 `body { overflow-x: hidden; }`，表格右侧可能直接被裁掉。
3. 《语义地形工程…》写着“五种常见地形问题”，正文实际列了六种，配图的无障碍标签也写成“五种”。这是明确的内容计数错误。
4. 两篇长文在 `.post-content` 内又套了一层 `.container`，320 px 下正文只剩 235 px；同一模板的其他文章能保留约 267 px。双重水平内边距让手机阅读区过窄。
5. 长文的宽幅 SVG 在手机上整体缩小，图中文字会从设计稿中的 11–14 px 缩到约 4–5 px。图形没有撑破页面，却已经难以阅读。
6. 旧文中关于 llama.cpp KV cache 的表述过于绝对，且缺少运行参数和日志依据。新文章发布时应补充适用条件，并从旧文链接到新文；不建议在没有原始日志的情况下改写旧数据。

### 3.2 《小 VLM 的 function calling 有多不稳定：一次 probe→stream 架构重构》

规模：约 6,015 个正文字符，7 个二级标题、3 个三级标题、1 张内联 SVG、3 个代码块和 4 张表格。320 px 窄屏下页面高度约 15,326 px。

做得好的地方：

- 给出成功/失败次数、延迟、会话轨迹和修复前后表格，工程复盘的证据密度很高。
- 代码块本身有 `overflow-x: auto`，长代码可以横向滑动。
- 文首已标出 2026-08 的现状，避免读者把 7 月原型当成当前架构。

本次可以安全修复：

- 第 221–223 行的 `.post-content > .container` 形成双重水平内边距。320 px 下普通段落宽度只有 235 px；去掉内层容器的水平 padding 后可恢复到约 267 px。
- 第 423–431 行的 Session 对比表在 320 px 下宽 330 px，从左侧 40 px 延伸到 370 px，超过 315 px 可视宽度。给所有 `.data-table` 增加可横向滚动的包装层，或在移动端设置明确的滚动容器。仅给 `table` 设置 `width: 100%` 无法解决最小内容宽度。
- `body` 会隐藏横向溢出，因此表格必须在自身容器内滚动；不应依赖整页横向滚动。
- 第 246 行 `TL;DR` 直接使用 `<h3>`，文档结构从 `h1` 跳到 `h3`。可以改成 `<h2>`，或改为没有标题语义的摘要标签。
- 四张表都缺少 `<caption>` 和表头 `scope`。

技术内容需要核证，先不要凭文字感觉改写：

- 第 520–558 行把命中条件写成“prompt 前缀字节级完全一致”，并称任何空格、换行变化都会导致“整个前缀 KV 重算”。模型实际处理的是 token 序列；字节一致通常能保证 token 一致，但缓存实现可能复用分歧点之前的公共 token 前缀。是否命中还取决于 llama.cpp 的运行方式、缓存开关、slot/sequence 的连续性、请求调度和上下文是否仍保留。
- 第 544 行强调“复用同一字符串对象”。对象身份不会进入模型请求；真正相关的是序列化后的文本和 token 前缀是否稳定。
- “700 tokens 降到 0”“首 token 节省 4–6 秒”“降低 30–60%”缺少模型版本、量化、硬件、上下文长度、服务启动参数、重复次数和日志字段。新文章发布时应补一张实验条件表；若原始日志不存在，改成“当时在该环境中观察到”。
- “小 VLM function calling 的固有不确定性”由少量会话示例推导，范围偏大。更稳妥的结论应限定在本次 MiniCPM-V 版本、提示词、解码参数和接口实现。
- “核心创新”“更底层、更优雅”带有自我评价。可以把重心放回可复现的改动与测量结果。
- Hermes 的冻结快照来源没有链接。需要补项目、文档或代码位置，避免读者无法核对。

新 KV cache 文章上线后，建议把这一节收成“当时的观察 + 已知适用条件 + 继续阅读”，并链接到新文。这样能修正理解，又能保留原型期证据。

## 4. 跨文章排版与无障碍

### 4.1 移动端

实测结果：

| 页面 | 390 px | 320 px | 结论 |
| --- | --- | --- | --- |
| 博客目录 | 无整页横向溢出 | 无整页横向溢出；卡片宽约 291 px | 目录页响应式正常 |
| 语义地形 | 无横向溢出 | 无横向溢出 | 代码会换行，但 SVG 文字太小 |
| 小 VLM | 无整页横向溢出 | 315 px 可视宽度被表格撑到 370 px | 必修 |
| 桌面上下文 | 无横向溢出 | 无横向溢出 | 正文双重 padding，阅读列过窄 |
| Claude Code 可视化 | 无横向溢出 | 无横向溢出 | iframe 能缩放，已有移动端高度规则 |

宽幅 SVG 的共同问题比“是否溢出”更隐蔽：`viewBox` 多为 680–760 px，手机上被缩到约 235–267 px，图中文字按比例缩小。新文章优先使用响应式 HTML/CSS 流程图，或准备移动端竖排版本；如果必须保留宽图，外层提供横向滚动、清晰的滑动提示和等价文字说明。

### 4.2 标题与长文导航

- 文章都只有 `main`，没有 `<article>`；日期用普通 `<span>`，没有 `<time datetime="…">`。
- 最长文章有 36 个标题节点，却没有目录、锚点或段落 ID。手机上回看某一节成本很高。
- 博客目录的文章标题用 `<strong class="article-card-title">`，屏幕阅读器无法按标题快速浏览文章列表。可以改为 `<h3 class="article-card-title">`，样式类无需变化。
- 新文章建议提供短目录，并给二级标题稳定的英文或拼音 ID。旧文可在不改正文的前提下逐步补齐。

### 4.3 表格、代码与图

- 现有 5 张文章表格都没有 `<caption>`，表头也没有 `scope`。
- 代码块能横向滚动，但没有“可横向滑动”提示，也不能通过 Tab 直接获得焦点。对确实会溢出的代码块，可以加入 `tabindex="0"` 和简短标签。
- 所有正文都没有 `<img>`；“图文并茂”目前主要由内联 SVG 完成。SVG 清晰、可版本控制，移动端文字尺寸需要单独设计。
- SVG 的 `aria-label` 是优点；下一步应使用 `<figure>/<figcaption>` 建立图文语义关系。

### 4.4 颜色对比度

线上计算样式显示：

- `.post-meta` 为 14 px、`#858b85`，背景为 `#f3f0e8`，对比度约 3.06:1，未达到普通文本 4.5:1。
- 蓝色提示框强调字 `#1a73e8` 在 `#f0f7ff` 上约 4.17:1。
- 黄色提示框强调字 `#e65100` 在 `#fff8e1` 上约 3.57:1。
- 对话框中的蓝色角色字约 4.21:1。

这些字都不足以按“大号文本”放宽标准。最安全的处理是把小号元数据和提示框强调色调深，并做一次全站视觉回归；正文色 `#666d67` 在纸色背景上约 4.67:1，刚好达到 AA。

### 4.5 筛选器与按钮

- 博客筛选按钮只用 `.active` 表示状态，没有 `aria-pressed`。初始化时应给“全部”设置 `aria-pressed="true"`，点击后同步更新其他按钮。
- `aria-label="按主题筛选"` 放在普通 `<div>` 上，建议加 `role="group"`。
- 返回顶部按钮位于表单外，不会造成当前 bug；模板仍建议统一写 `type="button"`，避免未来嵌入表单后出现默认提交。

## 5. 链接、搜索元数据与站点一致性

### 已通过

- 本地 HTML 链接和资源链接全部通过现有校验器。
- 所有 `target="_blank"` 链接都带 `rel="noopener noreferrer"`。
- 正式文章都有 description、canonical、OG、Twitter Card 和通用分享图。
- Claude Code 推荐文同时提供原页面和源仓库，来源链清楚。

### 需要决策或改进

- 用户维护入口是 Vercel 域名，canonical、OG URL、站点地图和 robots 却统一指向 `https://fjnuslw.github.io/`。这会告诉搜索引擎优先收录 GitHub Pages 版本。若 GitHub Pages 是主域名，可以保留；若 Vercel 才是主域名，应全站一次性迁移，不能只改新文章。
- 所有文章共用 `assets/og-evidence-ledger.png`。新 KV cache 文若有专属主图，建议同时用作 OG 图，并写清尺寸。
- 文章日期不是 `<time>`，也没有 `article:published_time`、`article:modified_time` 或 JSON-LD。可以先把 HTML 语义做好，再决定是否加结构化数据。

## 6. 统一写作风格建议

本次新文章可以直接采用以下约定，旧文按需渐进处理：

- 第一次出现缩写时给中文解释和一句用途，例如“KV cache（键值缓存）：保存已经计算过的注意力中间结果”。
- 后文统一写 `KV cache`；标题可保留 `KV Cache`。`Prompt/prompt`、`Function Calling/function calling` 也应各选一种正文写法。
- 元信息统一为中文，例如“约 15 分钟”，避免页面正文是中文、阅读时间却写 `15 min read`。
- 一段只推进一个判断。抽象判断之后立即给输入、过程、输出或数字例子。
- 把“核心、优雅、天然、稳定命中、固有”等评价词换成可观察条件；无法测量时明确写成个人经验。
- 用户已经提出避免“不是……而是……”句式。旧文中该结构较多，尤其集中在《桌面上下文…》；不要机械替换连接词，应重新拆分因果关系。
- 引用论文、论坛或项目时，就近说明它支撑哪条结论；文末再保留完整来源表。
- 引用外部图片时优先使用明确许可证或作者授权的素材，保留作者、原始链接、许可证和访问日期。无许可证素材可链接或嵌入，不重新托管。
