## 可用性观察

### 做得顺手的部分

1. **授权在第一屏可见。** 初始化输出、manifest、INDEX、XML 和 JSON 都显示 `research-only`。恢复任务时无需先猜测能否进入产品实现。
2. **状态生成无额外状态文件。** 两次渲染没有写入新的快照文件，case 文件继续充当可审计记录，降低双份状态漂移的机会。
3. **下一关口足够具体。** 初始 `next_gate` 指向 Q-001，并要求补充当前证据和更新 lane status，适合作为恢复后的第一步。
4. **人读与程序消费各有格式。** XML 较短，适合放入上下文；JSON 保留分类计数和 active 数组，方便宿主程序校验或展示。
5. **非严格验证适合早期反馈。** 案例刚创建也能获得退出码 0，同时所有缺口继续可见。它可以在研究途中充当结构检查，不能据此宣称研究完成。
6. **相对路径约束有效。** 本次越界读取被明确拒绝，错误信息包含解析后的目标，便于定位调用错误。

## 意外行为与改进建议

### 1. `--project-root` 需要预先存在

初始化器能够创建 `search/` 与 `specs/` 子树，却不会创建项目根。第一次使用时，这个前置条件容易漏掉。可选改法有两种：

- 在帮助和错误信息中给出 `New-Item -ItemType Directory ...` 或 `mkdir ...` 提示；
- 增加显式 `--create-project-root`，由调用者主动选择创建，保持默认行为谨慎。

直接静默创建任意根目录会扩大拼写错误的影响，因此显式开关更容易审计。

### 2. 初始计数把模板骨架算作实体

刚初始化时，状态显示 `tasks: completed=0/1`；验证摘要也显示 2 个 finding、1 个 decision、1 个 requirement、1 个 task 和 1 个 verification。对应文件内仍是方括号占位符，它们还没有形成研究结论或可执行任务。

这会给快速阅读者一种“已经产生一个任务”的印象。状态投影可以增加 `template_placeholders: true` 或分别报告 `scaffolded` 与 `grounded` 数量。更小的改动是把初始任务显示为 `draft=1, grounded=0`。相关判定需要保持确定性，例如依据未替换的模板标记，避免模型自行判断完成度。

### 3. manifest schema 与 projection schema 的版本号容易混看

manifest 使用 `0.2`，XML 根节点和 JSON 的 projection schema 使用 `0.1`。两者服务于不同契约，协议已经分别说明；单看输出时仍可能把它们当成一次降级。

可把投影字段命名得更完整，例如 `projection_schema="0.1"`，并在 XML 内增加 `case_schema: 0.2`。JSON 已采用 `projection_schema`，XML 目前只写 `schema`。

### 4. `as_of` 表达的是记录更新时间

状态的 `as_of` 来自 manifest 的 `updated_at`。案例文件未变时，多次渲染会保留同一时间。这能表达“数据最后更新于何时”，但名称也可能被理解为“这段投影何时生成”。

建议保留稳定的 `case_updated_at`，如宿主需要诊断缓存，再另加不参与决策的 `rendered_at`。若希望输出完全可复现，可只改名，不新增渲染时间。

### 5. XML 更接近带标签的紧凑文本块

根节点内部使用逐行文本，没有为 questions、sources、tasks 建立子元素。它保持短小，也能被 XML 解析器读取为文本节点；需要按字段编程消费时，JSON 更合适。文档可以直接称它为“XML 包裹的上下文块”，减少使用者对完整 XML 数据模型的期待。

## 安全边界判断

- **已观察到的保护：** case 路径在解析后必须留在 project root；状态渲染过程只读；授权字段在多处重复展示；检索内容没有进入初始投影；非严格验证不会把警告隐藏起来。
- **仍由宿主承担：** 把状态块放入哪一种消息角色、谁能修改 manifest、渲染与读取之间是否发生并发改动、输出进入模型前采用何种信任标签。
- **状态块能证明的范围：** 它能汇总文件当前记录的阶段、授权和计数。它无法单独证明来源可靠、研究已完成、用户确实授予实现权限或文件未被其他进程改写。交付结论仍需结合 case 文件与严格验证。
- **本次没有覆盖：** 恶意 XML 字符、损坏 JSONL、并发写入、符号链接绕过、长路径极限、严格验证完成态。这些需要专门的安全或兼容性测试，超出本次从空案例开始的前向使用路径。

## 最终安全审查后的回归

后续独立代码审查又构造了三类反例：`research-only` case 被写成 `implementing`、必需账本缺失或只保留状态字段、单文件符号链接指向材料根之外。第一次 projector 会把前两类部分输入显示为完整，授权组合还可能给出继续执行的下一关。维护者随后补齐跨字段与输入完整性检查。

最终回归结果如下：

1. `research-only + implementing/verified` 计入 `invalid_records`，下一关先要求运行 validator 并修复记录，不再输出执行未完成任务的指令。
2. 缺少 `sources.jsonl`、`traceability.csv` 或 `TASKS.md` 会进入完整性错误。
3. 来源记录需要完整 ID、问题归属、类型、权威级别、标题、URL、检索时间、状态和摘要；仅有 `status` 的 JSON 对象会被拒绝。
4. 追踪表需要精确表头，各状态还要满足对应的上游 ID 字段；仅有 `status` 一列的 CSV 会被拒绝。
5. manifest、来源账本、追踪表和任务文件会解析最终目标，并检查目标仍位于各自材料根内。
6. 单元测试扩展到 8 项：6 项在本机通过；2 项文件符号链接用例因 Windows `WinError 1314` 跳过。测试代码已经保留，具备权限的 Windows 环境和 Ubuntu CI 可执行。
7. 自用案例的严格校验继续通过，projector 输出 `invalid_records=0`，说明新增约束没有破坏现有 alpha.1 case 的读取路径。

上文“本次没有覆盖”描述的是第一次从空目录出发的使用范围。恶意 XML 字符已有输出转义；损坏 JSONL、缺失输入、授权冲突和最终文件目标已进入自动化回归。并发写入、长路径极限与真实宿主 checkpoint 恢复继续属于后续验证范围。
