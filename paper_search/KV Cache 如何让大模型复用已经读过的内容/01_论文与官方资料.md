# KV Cache 如何让大模型复用已经读过的内容：论文与官方资料研究笔记

> 调研日期：2026-08-12
>
> 用途：为个人网站的中文科普文章提供技术底稿
>
> 证据原则：优先采用原始论文、论文官方页面、项目官方代码和官方文档。2026 年的 “Models Take Notes at Prefill” 仍是 arXiv v1 预印本，相关结果单独标为实验性结论。

## 先给结论

1. KV Cache 保存的是每一层注意力模块为历史 token 算出的 Key 和 Value。历史 Query 已经完成了自己的任务，后续 token 不会再用到它们。
2. 因果掩码保证第 `i` 个 token 只能读取 `i` 及其之前的位置。只在末尾追加内容时，旧位置的计算结果不会被未来内容改写，因此可以原样复用。
3. Prefill 一次读入提示词并填满缓存；Decode 每步只处理新 token，同时读取全部历史 KV。缓存省掉了旧 token 的重复计算，但新 Query 仍需查看历史缓存，所以长上下文 Decode 依旧有线性读缓存成本。
4. 对普通 decoder-only Transformer，KV Cache 的逻辑大小可近似写成：

   ```text
   B × T × L × 2 × H_kv × D_head × s  bytes
   ```

   其中 `2` 代表 Key 和 Value。GQA/MQA 通过减少 `H_kv` 直接缩小缓存。
5. “KV Cache”描述缓存中的数据；“prompt cache / prefix cache”描述如何把这份数据跨请求保存、索引和复用。二者常用同一类张量，生命周期与管理方式不同。
6. Beam search 解决一条请求如何保留多条候选路径；continuous batching 解决多条请求如何在每个生成步动态进出批次。分页缓存、引用计数和写时复制让两类调度都更省内存。
7. 精确可靠的编辑包括：在末尾追加、从改动点截断后重算后缀、从共同前缀分叉。直接替换中间 token 后继续使用旧后缀，会留下与新内容不一致的缓存。
8. 把独立片段的缓存重新定位、拼接或局部刷新，是活跃研究方向。Prompt Cache、CacheBlend 和 2026 年的 programmable-kv 给出了不同方法，也共同显示了位置、跨片段依赖和边界 token 是主要限制。

## 1. KV Cache 究竟缓存什么，为什么只缓存 K 和 V

### 问题

一次自回归生成已经读过很多 token。下一步为什么可以跳过这些 token 的大部分计算？缓存里为什么通常没有历史 Query、注意力分数矩阵和完整 MLP 激活？

### 证据

标准自注意力在第 `l` 层把每个位置的隐藏状态投影为：

```text
q_i^(l) = h_i^(l) W_Q^(l)
k_i^(l) = h_i^(l) W_K^(l)
v_i^(l) = h_i^(l) W_V^(l)
```

生成第 `t` 个位置时，新 Query `q_t` 会和历史 Key `k_1 ... k_t` 计算匹配程度，再用这些权重汇总 `v_1 ... v_t`。Hugging Face 的官方缓存说明明确写出：每一步只需要当前 Query，新的 K/V 会追加到各层缓存，缓存张量沿序列维增长。文档给出的通用形状为 `[batch_size, num_heads, seq_len, head_dim]`。

现代 GQA 模型还需要一个修正：Query 头数和 K/V 头数可能不同。Hugging Face 的 Llama 实现用 `num_attention_heads` 生成 Query，用 `num_key_value_heads` 生成 K 和 V。这也是内存公式中应写 `H_kv` 的原因。

缓存按层保存。第 8 层的 K/V 来自第 8 层输入，第 20 层来自另一组隐藏状态，二者不能混用。历史 Query 只负责生成历史位置的输出；生成新位置时，计算需要的是新 Query 与历史 K/V。过去的注意力权重还会随着新 Query 改变，提前保存整张权重矩阵没有复用价值。

### 可用于文章的通俗解释

可以把一层注意力想成一次查资料：

- Key 像每段资料的索引标签，帮助新问题判断“该看哪一段”；
- Value 像索引指向的内容，决定最后取回什么信息；
- Query 是当前这一步提出的问题。

下一步会提出一个全新的问题，所以 Query 要重算；旧资料的标签和内容仍然有用，所以 K/V 留在缓存里。模型有很多层，相当于很多套逐层加工过的资料卡，每层都要保留自己的那一套。

### 写作边界

- 文中可说“KV Cache 通常保存每层历史 token 的 K/V 张量”。不同推理引擎还会附带块表、位置、量化尺度、引用计数等元数据。
- 不宜把 KV Cache 写成模型的长期知识库。它是某次模型运行产生的中间状态，依赖模型权重、层结构、位置和上下文。
- Hugging Face 说明页用 `num_heads` 展示概念形状；针对 GQA/MQA 模型应换成 `num_key_value_heads`。

## 2. Prefill 与 Decode 分别做什么

### 问题

“第一次读提示词”和“逐字生成答案”在计算形态上有什么差别？KV Cache 省掉了哪部分工作，还有哪部分成本保留下来？

### 证据

在常见的 decoder-only 推理流程中：

1. **Prefill**：把长度为 `P` 的提示词送入模型，批量计算各层所有位置的 K/V，并产出第一个待生成 token 的 logits。
2. **Decode**：每一步输入刚产生的新 token，计算它在各层的新 K/V，追加进缓存，然后让它的 Query 读取所有可见的历史 K/V。

Hugging Face 的官方说明将带缓存的单步注意力描述为随当前历史长度线性增长；没有缓存时，旧 token 的投影、注意力和后续层还会被反复执行。NVIDIA Dynamo 的官方设计文档也把 Prefill 和 Decode 分成两种工作阶段：前者通常更偏计算密集，后者通常更受读取 KV 的内存带宽影响。这里的“通常”取决于模型、序列长度、批量、硬件和内核实现。

只看标准稠密注意力对序列长度的数量级：

```text
首次 Prefill：O(P²)
缓存后的 G 步 Decode：O(GP + G²)
```

第二项来自 `P + (P+1) + ... + (P+G-1)`。若每一步都把增长后的整段序列重新执行一次，注意力部分会累加 `O((P+t)²)`，旧 token 的投影与 MLP 也会重复计算。

KV Cache 没有消除当前 Query 对历史 K/V 的读取。上下文越长，单步 Decode 需要扫描的数据越多。它也不会自动消除第一次 Prefill 的二次方注意力计算；只有命中跨请求的 prefix cache 时，已经缓存的前缀才可跳过 Prefill。

### 可用于文章的通俗解释

假设模型先读 4,000 个 token，再写 100 个 token：

- Prefill 像先把 4,000 页材料集中做成逐层索引；
- 第一次 Decode 拿第 4,001 个位置的问题查这套索引；
- 下一步只为新写出的那一页补索引，再读取已有 4,001 页；
- 缓存避免每写一个字就从第一页重新做索引。

这也解释了一个常见体验：首字等待时间主要受提示词 Prefill 影响，后续生成速度更容易受 KV Cache 读取量和批处理方式影响。

### 写作边界

- “Prefill 计算密集、Decode 带宽密集”适合作为常见工程规律，不能当成所有设备与序列长度下的定律。
- KV Cache 让单步历史注意力从“重算整段”变成“一个新 Query 读取历史 K/V”，并未让单步成本固定为常数。
- FlashAttention 降低一次注意力计算中的显存读写和中间矩阵占用；KV Cache 减少跨生成步骤的重复计算。两者可以同时使用。

## 3. KV Cache 的内存公式与一个可复算的例子

### 问题

为什么长上下文、并发请求和多路候选会很快吃满显存？怎样给读者一个不会把 MHA、GQA、MQA 混在一起的公式？

### 证据

对层结构相同、使用完整因果注意力的 decoder-only Transformer，缓存的逻辑大小可近似写成：

```text
M_KV = B × T × L × 2 × H_kv × D_head × s
```

| 符号 | 含义 |
|---|---|
| `B` | 同时保留缓存的序列数；beam 分支也算独立序列 |
| `T` | 每条序列缓存的 token 数 |
| `L` | 带缓存注意力的层数 |
| `2` | Key 与 Value 两份张量 |
| `H_kv` | Key/Value 头数 |
| `D_head` | 每个头的维度 |
| `s` | 每个元素的字节数，例如 BF16/FP16 通常为 2 |

假设一个示例模型有 32 层、8 个 K/V 头、头维度 128，缓存 4,096 个 token，并以 BF16 保存：

```text
1 × 4096 × 32 × 2 × 8 × 128 × 2
= 536,870,912 bytes
= 512 MiB / 序列
```

16 条同样长度的序列约需 8 GiB 逻辑 KV 空间。若其他参数不变，把 `H_kv` 从 8 换成 32，单序列会变成 2 GiB。这个例子只用于演示公式，不对应某个指定模型。

Shazeer 的 MQA 论文用一个共享 K/V 头服务多个 Query 头，目标之一就是降低增量解码时的 K/V 读取量。Ainslie 等人的 GQA 论文把 K/V 头数放在 MHA 与 MQA 之间，提供质量与速度的折中。Hugging Face Llama 源码也清楚地区分了 Query 头数和 K/V 头数。

### 可用于文章的通俗解释

KV Cache 像一个四个方向都会变大的仓库：

- 上下文翻倍，货架长度 `T` 翻倍；
- 并发翻倍，仓库份数 `B` 翻倍；
- 层数更多，每层都要留一套；
- K/V 头越多，每个 token 的资料卡越厚。

GQA 可以理解为让多组 Query 共用较少组 K/V 资料卡。它没有删掉历史 token，只是缩小了每个 token 在每层留下的卡片数量。

### 写作边界

上述公式没有计入：

- 分页最后一块的空位、块表、对齐和引用计数；
- 缓存量化所需的 scale 等元数据；
- tensor parallel 下各 GPU 的分片或复制策略；
- sliding-window、混合注意力和不同层拥有不同缓存上限的情况；
- speculative decoding 或多模型并行额外保留的状态。

因此它适合估算逻辑数据量，实际显存以引擎测量为准。

## 4. 因果掩码、位置编码与“从哪里开始失效”

### 问题

追加内容为什么能安全复用旧缓存？改动中间内容后，为什么不能只换掉一个位置的 K/V？把一段缓存挪到新位置又会遇到什么问题？

### 证据

Transformer 原始论文规定 decoder 的自注意力要遮住后续位置，使位置 `i` 的预测只能依赖更早的已知输出。Hugging Face 缓存说明由此得出直接结论：未来 token 加入后，过去 token 的表示不会改变，所以过去 K/V 可以在追加生成时复用。

这也给出了精确失效边界。若修改位置 `k`：

- `1 ... k-1` 看不到未来的 `k`，其缓存仍然有效；
- `k` 的 K/V 已经变化；
- `k+1 ...` 原先读取过旧的 `k`，每一层的隐藏状态都可能随之变化。

因此通用且精确的做法是保留 `k` 之前的缓存，从 `k` 开始重新 Prefill。仅替换第 `k` 个位置会让后缀继续携带旧上下文留下的状态。

位置还会进入缓存。RoPE 论文通过旋转 Query 和 Key 注入位置信息；Hugging Face Llama 代码先对 Q/K 应用旋转位置编码，再把 K/V 写入缓存，并用 `past_seen_tokens` 推导新位置。由此可见，直接把已经旋转过的 Key 从位置 100 搬到位置 1,000，Key 仍带着旧位置的相位。

对标准 RoPE，Value 没有接受同样的直接旋转操作，但它来自带有上下文和位置信息的隐藏状态。文章中可写“RoPE 主要需要校正 Key 的旋转”，同时提醒读者：修正旋转只处理了位置坐标，无法补回独立 Prefill 时缺失的跨片段注意力。

增量解码仍需正确的因果掩码和位置索引。Hugging Face 文档要求注意力掩码长度覆盖 `past_kv_length + new_tokens_length`；缓存本身不会替代掩码。

### 可用于文章的通俗解释

把缓存想成带页码的读书笔记：

- 在书末新增一页，前面的笔记不受影响；
- 改写第 20 页，第 21 页以后凡是引用过它的笔记都有可能过期；
- 把第 20 页的笔记直接贴到第 200 页，笔记里的页码关系还指向旧位置。

因此“追加”天然符合因果顺序；“中间改写”需要重算受影响的后缀；“移动和拼接”还要同时处理位置与上下文依赖。

### 写作边界

- “相同文字”只有在相同 token、相同前置上下文、相同位置与相同模型配置下，才自然得到相同缓存。
- 某些模型使用绝对位置嵌入、ALiBi、RoPE 变体、滑动窗口或 MLA，位置处理方法不能直接套用标准 RoPE 的重旋转公式。
- 只要文章谈到任意位置剪贴 KV，就应明确说明这属于需要位置校正和依赖修复的研究问题。

## 5. KV Cache、prompt cache 与 prefix cache 的区别和关系

### 问题

这些词经常混在一起。怎样解释它们的关系，同时避免让读者以为任意相似文本都能命中缓存？

### 证据

可以按“数据”和“管理方式”分两层理解：

- **KV Cache**：历史 token 在各注意力层留下的 K/V 中间状态。它可以只活在一次请求的生成过程里。
- **Prompt/Prefix Cache**：推理服务把某段前缀的 KV Cache 留得更久，并建立索引，让后来的请求跳过相同前缀的 Prefill。

vLLM 的 Automatic Prefix Caching 文档用块哈希查找可复用前缀。每个块的键包含父块哈希、当前块的精确 token ID，以及会影响计算结果的额外信息，例如 LoRA 标识、多模态输入哈希和可选的 cache salt。vLLM 只缓存完整块。这个设计说明真正的匹配对象是模型计算所见的 token 序列和相关配置，不能简单概括成“原始字符串逐字节相同”。原始字节相同通常足以产生相同 token；不同字符串在特定 tokenizer 处理后也可能得到同一 token 序列。

llama.cpp server 的 `cache_prompt` 会把新 prompt 与槽位之前的 prompt 比较，只重新计算未见过的后缀；它还提供槽位缓存的保存、恢复和擦除接口。这证明工程上可以把缓存延长到后续请求，仍需绑定同一模型和兼容的运行时格式。

MLSys 2024 的论文 **Prompt Cache** 又向前走了一步。它为可复用模块分配预设位置，并允许提示词按 schema 组合。为让模块能独立计算，模块间缺失的依赖会被掩蔽或通过 scaffold 一起编码。论文明确把这种独立模块编码视为一种近似，并建议把有强依赖的内容放在同一模块中。

### 可用于文章的通俗解释

一次请求内的 KV Cache 像正在桌面上摊开的读书笔记。Prefix cache 像把常用开头的笔记装进带索引的抽屉：下一位读者从完全相同的开头出发，就能直接拿出笔记，继续处理后面的新内容。

例如很多请求都以同一份 3,000-token 系统提示词开头，服务可以保存这 3,000 个 token 的 KV。新请求若只在末尾增加用户问题，系统提示词对应的 Prefill 可以跳过。若中间插入一句话，命中通常只能延续到插入点之前。

### 写作边界

- “缓存命中”需要匹配所有会影响计算的条件。除 token 外，还可能包括模型权重版本、adapter、多模态输入、位置和注意力配置。
- Prefix cache 的常规能力是复用共同前缀。文本片段出现在句子中间或另一个位置，不会自动变成可复用前缀。
- 跨用户共享缓存可能泄露命中时间等侧信道信息。vLLM 提供 `cache_salt` 作为隔离信任域的一种机制。
- llama.cpp 的落盘缓存是引擎专用中间状态，不能当成跨模型、跨版本可携带的通用“记忆文件”。

## 6. Beam search、多路采样与分页缓存

### 问题

一条请求同时保留多条候选时，缓存如何复制和分叉？PagedAttention 解决了什么，是否减少了每个 token 必需的 K/V 内容？

### 证据

Beam search 在同一前缀后保留多个候选 token。候选刚分叉时拥有完全相同的历史缓存，后续各自追加不同 token。Hugging Face 的缓存实现提供 `batch_repeat_interleave`、`reorder_cache` 和 `batch_select_indices` 等操作，用于扩展 beam、按新排名重排缓存以及淘汰候选。朴素张量布局可能把共同前缀复制多份。

PagedAttention 论文把每条序列逻辑上连续的 KV 切成固定大小块，再允许这些块分散在物理显存中。每条序列通过块表找到自己的物理块。按需分配使内部碎片主要集中在最后一个未填满的块；共同前缀块还可以被多个序列引用。

vLLM 的官方说明用引用计数和写时复制管理共享块：多个候选先指向同一批前缀块，当某个候选要写入一个仍被共享的块时，再复制出自己的版本。这个机制同样适用于 parallel sampling。

PagedAttention 改善的是分配、碎片和共享。给定同样的模型和 token，逻辑上需要的 K/V 元素数量并没有凭空减少。真正缩小每个 token 缓存体积的手段包括 GQA/MQA、缓存量化、滑动窗口或其他模型结构变化。

### 可用于文章的通俗解释

把一条回答的缓存想成一摞活页纸。Beam search 在同一页之后尝试三个结尾：

- 共同的前 100 页可以让三个候选一起引用；
- 每个候选只添加自己的第 101 页；
- 候选被淘汰时，释放它独有的页面；
- 共享页面有人要改写时，先复印一份再写，这就是写时复制。

分页的价值在于活页可以放在不同抽屉，通过目录找到，不要求显存里预留一整段连续空间。

### 写作边界

- Beam search 的候选分支数会扩大活跃序列数，私有后缀仍会消耗额外缓存。
- 页大小过大增加末块浪费，过小会增加块表和调度开销；具体选择属于实现细节。
- PagedAttention 论文中的吞吐提升来自论文设定下与当时基线的实验，不宜写成所有模型和硬件都能得到固定倍数。

## 7. Continuous batching 与 KV Cache 如何配合

### 问题

Continuous batching 是否等同于 KV Cache？请求长度不同、到达时间不同，服务怎样在每一步重新组织批次？

### 证据

Orca 在 OSDI 2022 提出 iteration-level scheduling：调度器按模型迭代安排请求，而非等整个请求完成后才释放批次位置。已结束的请求可以退出，新到请求可以在后续迭代加入。Hugging Face 当前官方文档把 continuous batching 描述为每个生成步动态重排批次，并提供 token budget 与 chunked prefill 等设置。

这里有三层不同职责：

1. KV Cache 保存每条请求已经完成的历史计算；
2. 分页/块管理让不同长度的缓存可以动态增长、搬移和释放；
3. Continuous batching 调度器决定当前一步让哪些请求一起运行。

每个请求都有自己的当前位置、缓存长度和块表。调度器暂停一条请求后，只要它的缓存仍在，恢复时可以从上次位置继续；无需重新 Prefill。很长的 Prefill 可能挤占 Decode 的计算资源，因此一些引擎把 Prefill 切成较小块，与其他请求的 Decode 交错执行。

### 可用于文章的通俗解释

固定批处理像一辆车必须等最慢的乘客到终点，空座也不能换人。Continuous batching 像每到一站都重新排座：完成的请求下车，新请求上车，尚未完成的请求带着自己的 KV Cache 继续走。

KV Cache 是每位乘客的行李；分页系统负责行李放在哪个柜子；调度器负责这一站让谁上车。三个部分配合后，显卡才能持续处理长度不同的请求。

### 写作边界

- Continuous batching 是调度策略，KV Cache 是计算状态。拥有缓存并不会自动得到高效调度。
- Beam search 处理一条请求内部的候选分叉；continuous batching 处理多条请求的动态到达与完成。服务可以同时采用两者。
- Prefill 与 Decode 的混批效果受模型、硬件、token budget 和调度策略影响，不能只从是否启用 continuous batching 推断延迟。

## 8. FlashAttention、PagedAttention 与 KV Cache 各管哪一层问题

### 问题

这三个名称都围绕注意力和显存，文章怎样放在一起讲，才能避免概念重叠？

### 证据

FlashAttention 原始论文从 IO 复杂度出发，把注意力分块计算，减少 HBM 与片上 SRAM 之间的数据搬运，并避免显式保存完整的巨大注意力矩阵。它计算的是精确注意力，序列长度的标准稠密注意力算术数量级没有因此改变。

FlashAttention 官方仓库还提供 `flash_attn_with_kvcache`，用于迭代 Decode 中就地更新 KV Cache、应用 RoPE 并执行注意力。仓库说明也指出，当 Query 长度为 1 时，快速读取 KV 是关键瓶颈。这个工程接口说明 FlashAttention 内核可以直接围绕缓存做优化。

PagedAttention 管理缓存的地址和生命周期：逻辑 token 顺序连续，物理块可以不连续，还能共享与按需分配。KV Cache 则是被这些内核读取、被这些块管理器保存的数据本身。

### 可用于文章的通俗解释

可以用图书馆来区分：

- KV Cache 是已经整理好的资料卡；
- PagedAttention 是资料卡的活页柜与目录系统；
- FlashAttention 是查阅资料卡时更少往返仓库的读取流程。

三者在同一套服务中可以叠加使用：缓存避免重复制卡，分页减少空柜与重复副本，FlashAttention 减少一次查阅过程中的搬运。

### 写作边界

- 不要把 PagedAttention 的块管理效果归到 FlashAttention，也不要把 FlashAttention 写成跨生成步骤的缓存机制。
- “FlashAttention 更省显存”主要指注意力中间量与 IO；长生命周期的 KV Cache 仍然要占用显存。
- 当前仓库功能比 2022 年原始论文更丰富。介绍 paged KV、Decode 专用接口时应引用官方仓库，避免倒推成原论文已经包含全部后续能力。

## 9. “可编辑、可组合”到底能做到哪一步

### 问题

用户参考文章强调“KV Cache 未必是一次性的，可以编辑、组合”。哪些操作已经有稳定的因果依据，哪些仍依赖特定模型和实验方法？

### 证据

先把“编辑”拆成四种操作，结论会清楚很多。

| 操作 | 正确性与代价 | 适合怎样表述 |
|---|---|---|
| 末尾追加新内容 | 旧缓存保持有效；只为新 token 计算 K/V | 成熟、精确的标准操作 |
| 从位置 `k` 截断，再重算后缀 | 保留 `k` 以前的缓存；结果可与完整重算一致 | 通用、精确，代价取决于后缀长度 |
| 从共同前缀分叉 | 分叉前共享，分叉后各自追加；可结合写时复制 | beam、多路采样和请求 fork 的成熟做法 |
| 直接改中间 token，只刷新少量 K/V | 后缀可能仍含旧依赖；结果依赖方法、模型和任务 | 实验性近似，需要验证 |

2026 年的预印本 **Models Take Notes at Prefill: KV Cache Can Be Editable and Composable** 专门研究后两类更激进的操作。它把 Prefill 后的 KV 看作模型逐 token 留下的“笔记”，并报告了几项值得用于文章的观察：

1. **追加勘误通常较稳妥**：保留旧缓存，在尾部添加醒目的更正，让后续生成同时看到旧事实和新指令。底层操作仍是标准追加；模型是否遵从更正属于语义层行为。
2. **只改字段自身的 KV 容易留下陈旧后缀**：后续 token 已经把旧字段吸收到自己的层状态中，刷新单个字段无法普遍清除这些影响。
3. **局部原位刷新有条件**：论文在部分模型和任务上发现，显式 chain-of-thought 能让刷新后的字段在推理阶段重新被读取；没有这一步时可能被忽略。这个结果不能推广成任意模型都能可靠原位编辑。
4. **组合需要重新定位**：对标准 post-RoPE cache，论文对 Key 做位置重旋转，再拼接预编译片段，并在接缝附近做修复。论文报告的是高相似度与任务结果，没有证明数学恒等。
5. **强跨片段依赖会破坏独立编译**：若 B 片段本来需要在 Prefill 时读取 A，单独编译 B 会缺失这次交互。论文的交叉引用实验也显示，把相互依赖事实拆开会明显变难。

这篇预印本的结论与两项更早研究互相印证：

- **Prompt Cache（MLSys 2024）** 通过预分配位置和模块 schema 复用注意力状态，同时承认独立模块缺少跨模块注意力，建议把强依赖内容共同编码。
- **CacheBlend（EuroSys 2025）** 指出直接拼接独立缓存会缺失跨片段注意力，并选择部分 token 重算来恢复重要交互。它说明“只修位置”仍不够。

### 可用于文章的通俗解释

可以把一段 Prefill 后的 KV 当作模型边读边写下的多层笔记。

假设原文是：

```text
项目预算是 10 万元。后面三段都按 10 万元讨论人员和设备。
```

若把第一句改成 20 万元，只替换“10”的那张卡片，后面三段仍可能保留按 10 万元形成的笔记。精确做法是从预算数字处开始重算。另一种便宜做法是在末尾追加：

```text
勘误：当前预算以 20 万元为准，忽略前面的 10 万元。
```

模型有机会在回答时采用新信息，旧笔记仍然存在，因此这更接近“追加一条覆盖指令”。它的可靠性需要通过具体模型和任务测试。

组合也有类似问题。把“人物表”和“事件表”的缓存分开预制后再拼接，位置可以校正；如果事件表中写着“他把那份文件交给她”，独立 Prefill 时没有人物表，代词关系从未进入它的缓存。接缝重算或选择性重算正是为了补回这类交互。

### 写作边界

- 2026 年论文是单作者 arXiv v1 预印本，提交于 2026-06-14，尚不能当成经过广泛复现的通用工程结论。正文宜使用“作者在测试模型和任务上报告”。
- 论文要求模型暴露逐 token、逐层注意力 K/V。纯 SSM、循环状态模型或其他压缩状态结构无法直接套用；滑动窗口、MLA、RoPE 变体和混合层也需要专门适配。
- “可编辑”应说明是哪一种操作。追加勘误、截断重算、局部刷新和任意原位修改拥有不同的正确性保证。
- “可组合”也应说明误差来源。位置重旋转解决坐标问题，接缝修复与选择性重算处理一部分上下文问题，仍可能遗漏长距离跨块依赖。
- 预印本中的加速数字来自特定测试配置。若正文没有完整交代模型、任务、上下文和基线，建议不引用倍数。

## 10. 建议正文采用的能力分层

为了让文章既有想象力又不越过证据，可以按以下三层写：

### 第一层：已经成熟的基础能力

- 在同一次自回归生成中追加 K/V；
- 从相同前缀继续生成；
- 相同 token 前缀跨请求命中 prefix cache；
- beam 或多路采样共享共同前缀；
- 分页、引用计数、逐步释放与 continuous batching。

### 第二层：结果精确，但需要重算一部分

- 改动中间 token 后，从第一个改动位置截断并重算后缀；
- 根据模型的位置规则重新 Prefill 被移动片段；
- 为组合片段重算接缝或整个受影响区域。

### 第三层：研究中的近似操作

- 用末尾勘误在语义上覆盖旧信息；
- 只刷新字段或少量 token；
- 对独立缓存块做位置重旋转后直接拼接；
- 选择少量 token 重算来近似恢复跨块注意力。

正文可以把第三层写成“模型中间状态开始出现类似可编程资料结构的可能性”，并紧跟适用条件与失败例子。这样能保留参考文章最有启发性的部分，也能让读者分清标准推理能力和研究原型。

## 11. 可直接用于配图的图意

### 图 A：一条序列从 Prefill 到 Decode

```text
Prompt: [A][B][C][D]  --一次 Prefill-->  每层缓存 K_A..K_D / V_A..V_D
                                             |
Decode 1:                                新 Query_E 读取 A..D，写入 K_E/V_E
                                             |
Decode 2:                                新 Query_F 读取 A..E，写入 K_F/V_F
```

图注应强调：历史 Q 不保留；每一步都新增一格 K/V；新 Query 仍读取整段历史。

### 图 B：改动的精确失效边界

```text
旧序列： [A][B][C][D][E]
改动后： [A][B][X][D][E]
可复用：  ✓  ✓
需重算：        ↑  从 X 开始到末尾
```

图注应解释：D/E 的字面文本没有变化，它们原来的隐藏状态读取过 C，因此仍可能失效。

### 图 C：三类工程组件

```text
KV Cache          保存什么：各请求的历史 K/V
PagedAttention    放在哪里：块表、共享、写时复制
Continuous batch  何时运行：每步选择当前活跃请求
```

### 图 D：组合缓存的两道关

```text
片段 A 的缓存 + 片段 B 的缓存
        |             |
        +-- 位置关：B 的 Key 仍带旧位置
        +-- 依赖关：B 独立 Prefill 时没有读取 A
```

位置重旋转主要处理第一道关；边界重算或选择性重算用来补回第二道关的一部分。

## 13. 最后核对：适合写进正文与需要加限定的表述

| 表述 | 建议 |
|---|---|
| “KV Cache 保存每层历史 token 的 K 和 V” | 可以直接写，补充 GQA 的 K/V 头数可能少于 Query 头数 |
| “缓存后每步生成是 O(1)” | 删除；每个新 Query 仍读取随上下文增长的历史 K/V |
| “改一个字节就一定导致缓存全部失效” | 改成：token 化后的首个变化位置及其后缀通常需要重算；前面的因果前缀仍可复用 |
| “prompt cache 就是另一种数据结构” | 改成：它通常保存同类 KV 数据，并增加跨请求生命周期、索引与隔离策略 |
| “相同文本片段在任何位置都能复用” | 删除；位置、前置上下文和模型配置都参与缓存结果 |
| “PagedAttention 压缩了每个 token 的 K/V” | 删除；它主要改善分配、碎片与共享 |
| “KV 可以任意编辑和拼接” | 加限定；精确编辑需要截断重算，局部刷新与跨块组合仍有模型和任务边界 |
| “追加勘误等于删除旧事实” | 改成：旧 KV 仍在，新增指令可能在后续注意力中覆盖它的语义影响 |
| “2026 论文已经证明 KV 是通用可编程记忆” | 改成：预印本在若干模型和任务中展示了可编辑、可组合的实验原型 |
